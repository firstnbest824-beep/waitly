# Waitly Product Account Plan

Status: planning for non-core product work. This document is implementation guidance only; it does not define UI copy or implement UI.

## Purpose

Waitly's core loop is already defined as: wrap an AI CLI, detect content-free AI work lifecycle states, show a separate sponsored window during AI work, auto-close that window when the wrapped process ends, and allocate part of ad revenue toward the user's chosen technical funding target.

This plan covers the remaining account and product surfaces needed for a pilot:

- Login and identity.
- Personal donation credit and donation total.
- All-user cumulative donation total.
- Donation rooms.
- Sponsor creation and admin boundary.
- Opt-out behavior.
- Pilot reporting.

## Product Principles

- A user can run Waitly without creating an account, but account-only features need login.
- Donation credit belongs to the funding target, not to the user as withdrawable money.
- Any monetary value shown before sponsor settlement must be labeled as estimated.
- Users choose the funding route: direct target or donation room.
- Sponsors cannot self-publish ads in the pilot.
- Reports must explain funding flow without exposing prompts, code, terminal output, or per-user behavior to sponsors.

## Terms

User account: A signed-in identity that can sync settings, select funding routes, join rooms, and view personal donation credit history.

Install identity: A local anonymous ID generated by the CLI wrapper. It may accrue local estimated credit before login, but it is not enough for cross-device account features.

Donation target: The final beneficiary category or verified beneficiary that receives the funding allocation. Examples: open source project, researcher, technical community, developer education group.

Donation room: A shared pool users can join. A room routes its members' eligible Waitly donation credit toward one selected target or reviewed target category and shows cumulative room progress.

Donation credit: The internal estimated amount attributed to eligible ad events. It is not cash owed to the user.

Sponsor: The advertiser or partner funding a campaign.

Campaign: An admin-approved sponsored placement with creative, destination URL, eligibility rules, budget, and reporting rules.

## Identity And Login

### MVP Login Scope

Login is required for:

- Personal cross-device donation totals.
- Room creation, ownership, and membership.
- Syncing selected donation route across installs.
- Exporting personal pilot contribution history.
- Admin or sponsor operations.

Login is not required for:

- Running `waitly run ...`.
- Local opt-out.
- Using local pause or disable controls outside the ad window.
- Viewing the public all-user total.

### Identity States

Anonymous install:

- Has `install_id`.
- Can store local settings and selected donation route.
- Can generate eligible ad events.
- Can show local-only estimated donation credit.
- Cannot create rooms or act as room owner.

Signed-in user:

- Has `user_id`.
- May link one or more `install_id` values.
- Can sync selected route and opt-out state.
- Can view personal totals across linked installs.

Admin:

- Has `user_id` plus `admin` role.
- Can approve donation targets, rooms, sponsors, campaigns, creatives, and reporting exports.

Sponsor operator:

- Future role only unless explicitly enabled.
- In the pilot, sponsor-submitted forms create leads/proposals only; they do not create live campaigns.

### Anonymous Credit Merge

On first login, the product should offer to attach eligible local events from the current install to the signed-in user.

Implementation requirement:

- Do not silently attach historical local activity to a login.
- Attach only content-free event records.
- Preserve event timestamps, campaign IDs, route IDs, and eligibility status.
- Never attach terminal output, prompts, source code, command arguments, paths, or environment data.

Open decision:

- Whether the first pilot skips historical merge and starts account totals only after login.

## Donation Credit Ledger

### Ledger Semantics

Donation credit is a ledger, not a counter mutated in place. Each eligible ad event creates a ledger entry that can later be confirmed, rejected, adjusted, or settled.

Suggested ledger fields:

```text
donation_ledger_entry
- id
- created_at
- event_id
- install_id
- user_id nullable
- room_id nullable
- donation_target_id nullable
- campaign_id
- sponsor_id
- amount_minor
- currency
- status: pending | confirmed | rejected | adjusted | settled
- reason_code
- reporting_period
```

Rules:

- `pending` means estimated and not ready for public settled reporting.
- `confirmed` means eligible after fraud and campaign checks.
- `rejected` means the event should not count.
- `adjusted` corrects a prior entry without overwriting it.
- `settled` means included in a sponsor or pilot settlement report.

### Eligibility Inputs

The exact formula is a pricing decision, but implementation should support these inputs:

- Campaign budget and rate.
- Eligible impression count.
- Eligible click count, if the campaign uses clicks.
- Dedupe and frequency caps.
- Opt-out state at event time.
- Fraud or automation flags.
- Funding route selected at event time.

Product rule:

- Do not design the user experience around maximizing clicks. Donation credit should primarily reward eligible sponsored exposure, not click farming.

### Personal Total

The personal total is the user's cumulative estimated or confirmed contribution toward chosen targets.

Required views for future UI/API:

- Lifetime estimated total.
- Current reporting-period estimated total.
- Confirmed total.
- Settled total.
- Breakdown by target.
- Breakdown by room.

Required labels:

- Pre-settlement values must say "estimated".
- Values must not imply the user can withdraw the money.
- Totals must state that part of sponsor revenue funds the selected target.

### All-User Cumulative Total

The all-user total is a public aggregate of Waitly donation credit across all users.

Recommended definition for pilot:

- Public headline total: confirmed donation credit across all pilot users.
- Secondary metric: estimated pending credit for the current period, if shown separately.

Privacy rules:

- Do not expose per-user data.
- Do not show a target or room subtotal publicly until it meets a minimum cohort threshold.
- Use reporting-period labels so the number is not confused with settled cash paid.

Open decision:

- Minimum public threshold for a room or target subtotal.

## Donation Rooms

### Purpose

Donation rooms let users coordinate funding around a shared target, project, community, or theme without changing the core Waitly loop.

Examples:

- A team room funding an open source dependency.
- A conference room funding a developer education program.
- A research room funding AI safety or security research.

### Room Model

Suggested fields:

```text
donation_room
- id
- slug
- name
- description
- owner_user_id
- donation_target_id nullable
- target_category
- visibility: public | unlisted | private
- join_policy: open | approval_required | invite_only
- moderation_status: draft | pending_review | approved | rejected | archived
- created_at
- updated_at
```

Membership:

```text
donation_room_member
- room_id
- user_id
- role: owner | admin | member
- status: active | pending | removed
- joined_at
```

### Room Creation Rules

- User-created rooms start as `draft` or `pending_review`.
- A room can collect visible pilot credit only after review if it names a custom beneficiary.
- Rooms that select an already-approved target category may be approved faster.
- Room names, descriptions, and target claims require moderation.
- Room owners cannot edit ledger totals.

### Funding Route Rules

A signed-in user can choose one active funding route:

- Direct donation target.
- Donation room.

An anonymous install can choose:

- Default target category.
- Local saved target.

When a user selects a room:

- New eligible credit routes to the room's target.
- Historical credit remains with the route active at the time of the event unless a future migration rule is approved.

### Room Totals

Room totals should include:

- Estimated current-period credit.
- Confirmed current-period credit.
- Lifetime confirmed credit.
- Member count, if cohort threshold is met.

Do not show:

- Per-member contribution rankings in the pilot.
- Raw event logs.
- Prompt, code, command, or repository context.

Open decision:

- Whether rooms can be private in the first pilot or whether all pilot rooms must be admin-created.

## Sponsor Creation And Admin Boundary

### Pilot Boundary

Sponsors cannot create live campaigns directly in the pilot.

Allowed sponsor-facing action:

- Submit interest or campaign proposal.

Admin-only actions:

- Create sponsor record.
- Approve sponsor identity.
- Create or edit campaign.
- Upload or approve creative.
- Set campaign budget, rate, dates, caps, targeting, and destination URL.
- Mark a campaign live.
- Pause or archive a campaign.
- Export sponsor reporting.

### Required Audit Trail

Every admin action that changes sponsor, campaign, creative, rate, or reporting status should record:

```text
admin_audit_event
- id
- actor_user_id
- action
- entity_type
- entity_id
- before_summary
- after_summary
- created_at
```

### Donation Target Boundary

Donation target creation is separate from sponsor creation.

Users may suggest donation targets, but admin review is required before:

- The target appears as verified.
- A room can publicly claim a named beneficiary.
- Any settlement report uses the target as payable.

Open decision:

- Verification requirements for donation targets before payout.

## Opt-Out Behavior

### Sponsored Window Lifecycle

The sponsored window itself has no close button and no pause or disable controls. It opens during wrapped AI work and auto-closes when the wrapped AI process ends.

Pause and disable controls must live outside the ad window, such as CLI flags, local config, account settings, or another non-ad control surface.

### Controls

Waitly should support layered controls:

- Pause sponsored-window opens for the current run.
- Pause sponsored-window opens until tomorrow.
- Disable sponsored windows globally.

The exact UI can be designed later, but the state machine should be supported.

### Product Behavior

When disabled globally:

- `waitly run ...` still runs the wrapped command.
- No new sponsored windows open after the disabled state is active.
- Any already-open prototype sponsored window still auto-closes when the wrapped process exits; do not add an in-window close control.
- No impression or click donation credit accrues.
- Wait detection may continue only if needed for local product operation and must remain content-free.
- Settings persist locally.
- If signed in, settings sync to the account after explicit login.

When paused for a run or day:

- No new sponsored windows open during the pause period.
- The pause should expire automatically.
- The CLI should not ask repeatedly during the same pause.

### Event Logging

Allowed lifecycle and opt-out events:

- `sponsor_window_auto_closed`
- `sponsor_window_paused`
- `sponsor_window_disabled`
- `sponsor_window_enabled`

Events must not imply that the user closed the popup from inside the sponsored window, and must not include prompts, code, terminal output, command arguments, paths, or environment variables.

## Pilot Reporting

### Audiences

User report:

- Personal estimated and confirmed donation credit.
- Active funding route.
- Breakdown by target and room.
- Opt-out state.

Sponsor report:

- Aggregated impressions.
- Aggregated eligible impressions.
- Aggregated clicks, if applicable.
- Auto-close counts.
- Opt-out rate.
- Estimated donation credit funded.
- Confirmed donation credit funded.
- Target or category breakdown where cohort thresholds are met.

Beneficiary or room report:

- Confirmed donation credit attributed to the target or room.
- Reporting period.
- Sponsor names if contractually allowed.
- Number of contributing users only if cohort threshold is met.

Internal pilot report:

- Active installs.
- Signed-in users.
- Wait events.
- Sponsored window opens.
- Eligible impression rate.
- Auto-close counts.
- Pause and global opt-out rate.
- Donation target selection rate.
- Room creation and join rate.
- Estimated, confirmed, rejected, and settled credit.
- Sponsor campaign performance.

### Reporting Requirements

- Reports must be generated from ledger and content-free event data.
- Sponsor reports must be aggregate only.
- Reports must label estimated versus confirmed versus settled values.
- Reports must include date range, currency, and campaign scope.
- Reports must not include prompt text, source code, terminal output, file paths, repo names, or raw command arguments.

## Implementation Backlog

1. Identity foundation:
   - Add account model, install linking model, and role model.
   - Support anonymous local mode and signed-in mode.
   - Acceptance: `waitly run` works without login; signed-in user can link an install without content data.

2. Donation ledger:
   - Add append-only ledger entries from eligible ad events.
   - Add aggregate queries for personal, room, target, and all-user totals.
   - Acceptance: totals can be recalculated from ledger entries.

3. Funding route selection:
   - Persist active route as direct target or room.
   - Acceptance: new eligible ledger entries use the route active at event time.

4. Donation rooms:
   - Add room, membership, visibility, join policy, and moderation status.
   - Acceptance: a signed-in user can own a reviewed room and members' new credit can route to it.

5. Sponsor admin boundary:
   - Add admin-only sponsor, campaign, and creative state changes with audit events.
   - Acceptance: non-admin sponsor submissions cannot create live campaigns.

6. Opt-out state:
   - Add local and account-level sponsored-window settings.
   - Acceptance: sponsored windows have no in-window close control, auto-close on wrapped process exit, and global disable prevents windows and donation credit without breaking wrapped CLI execution.

7. Pilot reporting:
   - Add aggregate report generation from ledger and event tables.
   - Acceptance: sponsor report contains no per-user data and no prompt/code/output fields.

## Open Decisions

- Auth provider and MVP login methods.
- Whether anonymous historical credit can merge into a new account.
- Exact donation credit formula and sponsor pricing model.
- What qualifies as an eligible impression.
- Minimum cohort threshold for public target, room, and sponsor reporting.
- Donation target verification and payout requirements.
- Whether user-created rooms are included in the first pilot.
- Whether sponsor names are visible in beneficiary reports.
- Reporting cadence for pilot sponsors and beneficiaries.
- Currency and tax treatment for settled funding.
- Exact external control surfaces for pause and disable in the prototype.
