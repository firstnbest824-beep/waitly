# Waitly Trust Policy

Status: planning policy for implementation and pilot operations. This document sets product and engineering constraints; it is not legal advice.

## Purpose

Waitly must avoid looking or behaving like adware. The trust contract is simple:

- Ads appear only in a separate sponsored window.
- In the current prototype, sponsored windows do not include an in-ad close button; they open during AI work and auto-close when the wrapped process ends.
- A durable opt-out or pause control should exist outside the ad window before pilot launch.
- Users choose the donation target or room.
- Waitly does not collect prompt text, source code, terminal output, command arguments, file paths, environment variables, or repository contents.
- Sponsors receive aggregate reports only.

## Non-Negotiable Rules

- No ads inside terminal output.
- No code or prompt collection.
- No terminal output collection.
- No command argument, file path, environment variable, clipboard, browser history, screen capture, or keylogging collection.
- No hidden sponsored placement.
- No sponsor self-publishing in the pilot.
- No sponsor access to raw user logs.
- No fixed revenue-share claim until pricing and settlement are approved.
- No donation total may imply money is withdrawable by the user.

## Data Collection Policy

### Allowed Data

Waitly may collect or store only content-free operational data needed for the pilot:

- Random install ID.
- Signed-in user ID and account metadata.
- App version.
- Operating system family and architecture.
- Event timestamps.
- Wait detector state labels, such as `waiting_started` and `waiting_ended`.
- Wait duration in milliseconds.
- Sponsored window event labels, such as `opened`, `auto_closed`, `paused`, `disabled`, `clicked`.
- Campaign ID, creative ID, sponsor ID, donation target ID, and room ID.
- Selected funding route.
- Opt-out state.
- Donation ledger amount, currency, status, and reporting period.
- Aggregated pilot reporting metrics.

### Disallowed Data

Waitly must not collect, persist, transmit, or report:

- Prompt text.
- Source code.
- Terminal output content.
- Raw command arguments.
- File names or file paths.
- Repository names or remote URLs.
- Environment variables.
- API keys, tokens, secrets, or credentials.
- Clipboard contents.
- Keystrokes.
- Screen contents or screenshots.
- Browser history.
- User project files.
- AI model responses.

### Detector Requirement

Wait detection must operate as a content-free state machine.

Allowed:

- Detect that output is active or idle.
- Detect elapsed time since last output.
- Emit state labels and durations.

Not allowed:

- Persisting output lines.
- Sending output lines to a server.
- Hashing prompt or code text for later matching.
- Parsing user code or prompt content for ad targeting.

## Event Schema Guardrails

Event schemas should use allowlists. A field is not allowed just because it is convenient.

Allowed event field categories:

- IDs generated by Waitly.
- Timestamps.
- Enumerated state names.
- Durations.
- Version and platform metadata.
- Campaign, creative, target, room, and ledger references.
- Boolean or enum settings states.

Fields that should trigger review if proposed:

- `prompt`
- `code`
- `output`
- `stdout`
- `stderr`
- `command`
- `args`
- `path`
- `filename`
- `repo`
- `url`, except approved sponsor destination URLs in campaign records
- `env`
- `token`
- `secret`
- `clipboard`
- `screenshot`

Acceptance requirement:

- Any new telemetry/event field must be reviewed against this policy before pilot use.

## Sponsored Label Rules

Every paid placement must clearly show that it is sponsored.

Required:

- A visible `Sponsored` label in the sponsored window.
- Sponsor name or brand identity.
- Destination action that makes clear the user is leaving or opening sponsor content.
- Clear auto-close behavior tied to the wrapped AI process lifecycle.
- A settings-level pause/disable control outside the ad window before pilot launch.
- No close, pause, or disable control inside the sponsored window itself.
- No visual treatment that impersonates the terminal, AI assistant output, OS security alerts, or package manager output.

Not allowed:

- Hidden ads.
- Native-looking content without a sponsored label.
- Countdown locks.
- Forced interaction before returning to work.
- Misleading system-style warnings.
- Copy that implies Waitly endorses a claim beyond the approved creative.

## Ad Quality Rules

### Allowed Sponsor Categories

Pilot sponsors should fit developer, technical, research, or education contexts:

- Cloud infrastructure.
- Databases.
- APIs.
- Security tools.
- Monitoring and observability.
- Deployment and hosting.
- AI developer tools.
- SaaS products for developers.
- Developer education.
- Technical hiring or freelance platforms.
- Open source services.

### Disallowed Sponsor Categories

Disallow:

- Malware, spyware, or unwanted software.
- Adult content.
- Gambling.
- Deceptive financial products.
- High-risk get-rich or trading claims.
- Political persuasion.
- Hate, harassment, or discriminatory content.
- Counterfeit products.
- Illegal goods or services.
- Misleading health claims.
- Forced downloads.
- Browser extensions or agents that require invasive permissions without review.
- Ads that ask users to paste prompts, source code, keys, tokens, or private project data.

### Creative Review Checklist

Before a campaign can go live, an admin should confirm:

- Sponsor identity is known.
- Creative has a visible sponsored label.
- Destination URL uses HTTPS.
- Destination page matches the creative claim.
- No forced download starts on click.
- No prompt, code, secret, or repository upload is requested as the first required action.
- The claim is concrete and not deceptive.
- The creative is relevant to developers or technical work.
- Donation language uses "part of sponsor revenue" or equivalent until exact terms are approved.

## Opt-Out Policy

Users must be able to pause or disable sponsored windows without breaking the wrapped CLI command. For the current prototype, the sponsored window itself must not include a close button or opt-out controls. It opens during wrapped AI work and auto-closes when the wrapped AI process exits.

Required controls:

- Pause sponsored-window opens for the current run outside the ad window.
- Pause sponsored-window opens until tomorrow outside the ad window.
- Disable sponsored windows through settings, config, or environment.
- Keep all pause and disable controls outside the sponsored window.

Behavior when disabled:

- Do not open new sponsored windows after the disabled state is active.
- Any already-open prototype sponsored window still auto-closes when the wrapped process exits; do not add an in-window close control.
- Do not count impressions.
- Do not create donation credit from impressions or clicks.
- Continue running the wrapped command normally.
- Persist the preference locally.
- Sync the preference to the signed-in account only after login.

Allowed logging:

- Record that the setting changed.
- Record timestamp and setting state.

Disallowed logging:

- Recording why the user opted out unless they explicitly submit feedback.
- Recording prompt, code, terminal output, command arguments, paths, or environment variables with the setting event.

## Sponsor And Admin Boundary

Pilot sponsor creation and campaign publishing are admin-only.

Sponsors may:

- Submit interest.
- Provide creative and destination details for review.
- Receive aggregate campaign reports.

Sponsors may not:

- Create live campaigns directly.
- Change donation allocation directly.
- Upload or switch live creatives without admin approval.
- See raw user events.
- See per-user contribution data.
- Target ads based on prompts, code, repository contents, file paths, or command arguments.

Admins must:

- Approve sponsor identity.
- Approve creative.
- Set budget, dates, caps, rates, and destination URLs.
- Pause campaigns that violate policy.
- Maintain audit trails for sponsor and campaign changes.

## Donation And Reporting Policy

Donation totals must be transparent and conservative.

Required labels:

- Estimated: eligible but not settled.
- Confirmed: validated for the reporting period.
- Settled: included in sponsor or pilot settlement.

User-facing rules:

- A user's personal total is contribution credit toward chosen targets.
- It is not cash owed to the user.
- The active target or room must be visible wherever practical.

Public reporting rules:

- All-user totals must be aggregate.
- Room and target totals should require a minimum cohort threshold.
- Public totals must state date range and whether values are estimated, confirmed, or settled.

Sponsor reporting rules:

- Aggregate only.
- No prompt, code, terminal output, raw command, path, repo, or per-user data.
- Include impressions, eligible impressions, clicks if applicable, auto-close counts, pause or opt-out rate, and donation credit funded.

Beneficiary reporting rules:

- Show reporting period, confirmed or settled donation credit, and high-level source categories.
- Do not expose individual users unless a user explicitly chooses to be named in a future feature.

## Abuse And Fraud Policy

Waitly should reduce abusive impressions and clicks without expanding data collection into sensitive content.

Allowed fraud signals:

- Event frequency.
- Duplicate event IDs.
- Impossible timing.
- Campaign cap violations.
- Install ID churn patterns.
- Repeated clicks from the same install or user.
- Sponsored window visibility duration.
- Known test or development mode flags.

Not allowed fraud signals:

- Prompt contents.
- Source code contents.
- Repository contents.
- Terminal output text.
- File paths.
- Private project metadata.

Product requirement:

- Avoid incentives that encourage users to click irrelevant ads just to increase donation credit.

## Incident Handling

If disallowed data is collected:

1. Stop the collection path.
2. Identify affected event types, storage locations, and time range.
3. Delete the disallowed data where feasible.
4. Rotate any exposed secrets if applicable.
5. Document the incident and fix.
6. Notify affected parties if required by law, contract, or pilot policy.

If a sponsor creative violates policy:

1. Pause the campaign.
2. Remove the creative from active rotation.
3. Preserve audit evidence.
4. Review whether any reports or totals need adjustment.
5. Require admin approval before reactivation.

## Implementation Acceptance Checks

Before pilot launch:

- Event schemas contain no disallowed data fields.
- Sponsored windows display a visible sponsored label.
- Sponsored windows have no in-window close button and auto-close when the wrapped CLI exits.
- External pause and disable controls work without stopping the wrapped CLI.
- Global opt-out prevents sponsored windows and donation credit.
- Sponsor reports are aggregate only.
- Admin audit events exist for sponsor, campaign, creative, and rate changes.
- Donation totals distinguish estimated, confirmed, and settled states.
- Campaign review checklist is complete for every live sponsor.

## Open Decisions

- Data retention period for raw content-free events.
- Minimum cohort threshold for room, target, and sponsor reporting.
- Whether users can opt into public attribution in a later release.
- Exact policy owner for sponsor approval.
- Formal privacy policy publication date for the pilot.
- Legal review requirements for donation wording and payout settlement.
